# October 31, 2026 research update

T1E2 remains the stable release. R003 is an experimental Recorder extension of
that baseline, with source recipes and exact output identities. No firmware,
sample bank, user recording, project or raw device capture is published.

A clean export of the public source reproduced R003's exact MAIN, DSP and final
SysEx from the three validated private inputs. This checks the public build
recipe; it does not expand the hardware validation scope below.

## Recorder progress

The port now covers capture, trim, audition, normalization, naming, saving,
assignment and Recorder reopening. R003 retains the six sample Machines and
T1E2 USB interface while excluding later USB/SPI timing experiments.

Hardware checks confirmed normal startup and stock audio, then a MAIN recording
saved as stereo 48 kHz audio. Complete file readback contained 196,923 frames
(about 4.10 seconds). Reopening Recorder retained the full waveform/trim range.
After saving, the Recorder was idle and its cached frame counter was zero;
verification used the saved file and retained view bounds, not that idle counter.

Hardware trimming remains in progress: audition confirmation, comparison of the
trimmed file with the selected original PCM range, and final reopening are still
pending. Power-cycle persistence and long-duration USB/dense-pattern tests were
not performed. Screen polling remained off during the bounded live reads.

Offline native instruction checks covered Recorder state transitions, retained
bounds, normalization/trim/save/reopen paths, scalar/SIMD adapter boundaries, and
six sample Machines with stereo, live controls and voice cleanup. These checks
execute selected instructions with fixtures; they do not establish hardware
cache coherency, DMA timing or complete real-time behavior.

## Confirmed MAIN-loader overlap

The conditional OS 1.11 loader stages compressed MAIN at `0x40200000`.
R002's expanding output overwrote unread compressed input at `0x40303372` in
native execution. Normal boot stages at `0x40400000` and did not show that
overlap. This finding does not establish the cause of earlier black-screen or
USB reports.

R003 separately compresses a 647,400-byte MAIN tail. An authored 80-byte entry
wrapper copies its 166,308-byte compressed representation into the existing
420,464-byte sampler runtime reservation, calls the stock decompressor, then
resumes original startup. Existing startup installs the runtime afterward.
There is no new RAM reservation or protected-loader modification.

Native checks exercised both actual outer depackers, the wrapper, register and
stack preservation, original SRAM initialization, six runtime copies and the
BSS clear. Minimum unread-input clearance was 32,911 bytes on the conditional
path and 2,130,063 bytes on normal boot. This is a bounded startup proof, not
whole-device emulation. R003 subsequently booted successfully on the device.

## SHARC audits and remaining uncertainty

The rule checker no longer treats RFRAME's `return-frame` annotation as a
branch. Real CALL/JUMP/RETURN checks remain. Source-store checks conservatively
report unresolved addressing and incomplete coverage instead of calling them
safe. Recovery auditing measures compressed-input clearance rather than only
comparing section sizes. See [offline audit usage](../research-audits.md).

Review of two late calls in relocated native DT2 loops established E2 mode and
matching callee context. Other loop-ISA, adjacent-branch fetch interpretation,
mixed-width runway and code/data classification questions remain explicit
reviews. Native provenance alone is not a blanket hardware-rule exemption.
The aggregate R003 audit remains **review**, with no hard failure; it is not a
clean bill of health or a stability designation.

The R003 DSP is unchanged from the Recorder-only R001/R002 backport. The loader
repair changes MAIN packaging and entry handling, not DSP audio processing or
USB control-frame ordering. Exact identities are in the
[R003 manifest](../../releases/r003.json); the [Recorder guide](../recorder.md)
provides build and usage steps.

The sample-loading documentation also distinguishes the private project test
bank from DT2 factory content. Both exact build targets still require that
unpublished bank; ordinary Transfer uploads do not substitute for it.
